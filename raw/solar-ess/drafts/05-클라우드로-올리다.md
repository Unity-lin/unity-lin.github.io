# 5편. 클라우드로 올리다

내 노트북에서만 도는 시뮬레이터는 노트북을 덮는 순간 멈춥니다. 데이터를 몇 달씩 쌓으려면 항상 켜져 있는 곳이 필요했고, 구글 클라우드(GCP)를 골랐습니다.

## 구성

- **Cloud Scheduler:** 30분마다 시뮬레이터를 깨웁니다.
- **Cloud Functions:** 시뮬레이터가 한 번 돌아 10개 지역 데이터를 만들고, 제 대시보드 서버로 보냅니다.
- **Firestore:** 배터리 충전량 같은 상태를 저장합니다. 함수는 매번 새로 시작하므로, 저장해 두지 않으면 배터리가 매번 50%로 돌아갑니다.

서버 없이 필요할 때만 도는 구조라 비용이 거의 들지 않습니다. 하루 48번 실행은 무료 한도 안입니다.

![시스템 구성](images/architecture.svg)

아래쪽 줄(Firestore → 조회 API)은 나중에 더했습니다. 서버가 데이터를 거부해도 원본이 남습니다.

## 배포하면서 막힌 곳

| 순서 | 증상 | 원인과 해결 |
| --- | --- | --- |
| 1 | 배포 직후 모든 요청이 500 오류 | 기본 DB가 아닌 `solar-system-db`를 만들어 놓고 코드는 기본 DB를 찾고 있었음 |
| 2 | 습도 100% 초과, 밤에 전압 220V 고정 | 값 범위 제한과 잡음 추가 |
| 3 | 영하에서도 배터리 충전 | 리튬 배터리는 0°C 아래 충전하면 손상되므로 충전 차단 |
| 4 | 함수가 엉뚱한 DB에 접속 | 라이브러리에 DB 이름을 위치 인자가 아닌 키워드 인자로 넘겨야 했음 |
| 5 | 낮 데이터 상당수가 서버에 저장 안 됨 | 서버가 배터리 상태로 충전·방전만 받고 대기·가득·방전완료를 거부. 서버 쪽 수정 예정 |
| 6 | 배포한 뒤 몇 주 동안 맑은 날 데이터만 쌓임 | 설정 파일에 실제 날씨 사용이 꺼져 있었음. 오류가 아니라 아무도 모름 |

가장 아팠던 건 맨 위 줄입니다. 시스템은 아무 오류 없이 잘 돌고 있었고, 그래서 오히려 아무도 의심하지 않았습니다.

## 데이터를 스스로 저장하기

대시보드 서버가 거부하거나 장애가 나면 그 데이터는 사라집니다. 그래서 시뮬레이터가 만든 데이터를 직접 저장하고, 조회 API로 여러 클라이언트가 가져가게 바꿨습니다.

- 로컬에서는 MongoDB(Docker), GCP에서는 Firestore를 씁니다. 저장 계층만 두 벌이고, 생성 코드와 조회 API는 하나입니다.
- 로컬에서는 `--interval 1` 옵션으로 1초마다 만들 수 있어, 하루치 테스트를 몇 분 만에 끝낼 수 있습니다.

**이번 편에서 배운 것:** 에러가 없다고 맞게 도는 것은 아니다. 쌓인 데이터를 직접 들여다봐야 한다.
